LinkedList<T>

A doubly linked list where each element is a LinkedListNode<T> holding references to its neighbours. Insertions and removals at a known node are O(1) — but there is no index, so random access costs O(n). A niche tool, rarely the right answer compared to List<T>.

Lookup
O(n)
no index, must traverse

O(1)
at a known node

When to use

LinkedList<T> pays off only when you do many inserts and removes in the middle of a sequence and already hold a reference to the node. For most scenarios, List<T> wins on cache locality and memory cost even when its O(n) mid-insert looks worse on paper. Use this collection for LRU caches, history trackers, and schedulers that splice nodes by reference — and reach for List<T> by default otherwise.

Node-based design
Each element is wrapped in a LinkedListNode<T> that stores Value along with Previous and Next references. Operations come in two flavours: value-based helpers (Find, Remove(T)) that walk the chain in O(n), and node-based helpers (AddAfter, AddBefore, Remove(node)) that are O(1) once you hold the node. The real speed comes from keeping node references, not values.

Example

// Create and populate
var tasks = new LinkedList<string>();
tasks.AddLast("compile");
tasks.AddLast("test");
tasks.AddLast("deploy");
tasks.AddFirst("plan");

// Traverse forward via First / Next
for (var n = tasks.First; n != null; n = n.Next)
    Console.WriteLine(n.Value);

// O(1) splice when you hold the node
LinkedListNode<string>? testNode = tasks.Find("test");   // O(n) search
if (testNode != null)
{
    tasks.AddAfter(testNode, "review");                // O(1)
    tasks.Remove(testNode);                              // O(1)
}

// Peek ends without removing
string? head = tasks.First?.Value;
string? tail = tasks.Last?.Value;

// Remove ends
tasks.RemoveFirst();
tasks.RemoveLast();

// Enumerate (yields values, not nodes)
foreach (string t in tasks)
    Console.WriteLine(t);
