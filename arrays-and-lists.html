Arrays & List<T>

The two workhorses of everyday C#. Fixed-length arrays stored in contiguous memory, and List<T> — an auto-resizing dynamic array that powers roughly 95% of the collection code you'll ever write on .NET 10.

01Overview

Both arrays and List<T> are sequential collections: items are stored contiguously in memory and can be reached by a zero-based index. The critical difference is who owns the size. An array fixes its length the moment you create it. A List<T> owns an internal array and transparently grows it for you — typically doubling in size when it fills up.

That single distinction shapes everything else: memory overhead, insert cost, search performance, even which LINQ operators are sensible. Understanding it is the foundation for every other data structure in this series.

Namespace

Arrays are part of the runtime itself — the System.Array base class lives in System. List<T> lives in System.Collections.Generic and ships with the BCL.

02The Array

An array is a fixed-length, strongly-typed sequence of elements allocated as a single contiguous block on the managed heap. Every element sits adjacent to its neighbours, which is why indexed access compiles down to nothing more than pointer arithmetic — O(1), cache-friendly, and about as fast as managed code gets.

Declaration

Program.cs · five ways to build an array 
// 1. Sized, default-initialised (zeros, nulls, false)
int[] scores = new int[5];

// 2. Inline initialiser
int[] primes = { 2, 3, 5, 7, 11 };

// 3. Target-typed new (C# 9+)
int[] days = new[] { 31, 28, 31, 30, 31 };

// 4. Collection expression — idiomatic in .NET 10
int[] vowels = ['a', 'e', 'i', 'o', 'u'];

// 5. Multi-dimensional
int[,] matrix = { { 1, 2 }, { 3, 4 }, { 5, 6 } };

Useful static helpers

Most operations on arrays live on the System.Array static class rather than as instance methods.

Array.* static helpers 
int[] numbers = [5, 2, 8, 1, 9, 3];

Array.Sort(numbers);                       // in-place  → [1, 2, 3, 5, 8, 9]
int idx  = Array.BinarySearch(numbers, 5);   // O(log n), sorted only
int[] dbl = Array.ConvertAll(numbers, n => n * 2);
Array.Reverse(numbers);
int found = Array.Find(numbers, n => n > 4);
int[] many = Array.FindAll(numbers, n => n > 4);

03The List<T>

List<T> is a thin, generic wrapper around an array that grows automatically. It is the default collection in .NET — if you don't know which collection to reach for, reach for this one.

Declaration

List<T> · five ways to build 
// 1. Empty
var cart = new List<string>();

// 2. Initialiser
var scores = new List<int> { 95, 82, 77 };

// 3. Pre-sized — avoids resize churn when final count is known
var buffer = new List<byte>(capacity: 1000);

// 4. Collection expression (C# 12+, idiomatic in .NET 10)
List<string> colors = ["red", "green", "blue"];

// 5. From another sequence
var copy = new List<int>(Enumerable.Range(1, 10));

Count vs Capacity

This is the single most important concept for understanding List<T> performance. Count is the number of items you actually have; Capacity is the length of the internal array backing the list. When Count reaches Capacity, the list allocates a new array roughly twice as large and copies every element across.

Observing capacity growth 
var list = new List<int>();

Console.WriteLine($"Count={list.Count}, Cap={list.Capacity}");
// Count=0, Cap=0    — nothing allocated yet

list.Add(1);
Console.WriteLine($"Count={list.Count}, Cap={list.Capacity}");
// Count=1, Cap=4    — first Add allocates 4 slots

for (int i = 0; i < 10; i++) list.Add(i);
Console.WriteLine($"Count={list.Count}, Cap={list.Capacity}");
// Count=11, Cap=16  — grew 4 → 8 → 16

Performance note

If you know the final count in advance, pre-size with the capacity constructor: new List<int>(capacity: 1000). You'll skip every doubling copy along the way. On hot paths that build large lists this saves real time and GC pressure.

05Side by side

Both expose indexing and iteration, but they are designed for different jobs.

Cache locality matters

Both types are stored contiguously, which means CPU prefetching works in your favour during iteration. Linear scans over a List<int> of 10,000 items are often faster than hash lookups in practice for small-to-medium data — measure before optimising.

07When to choose which

Pick T[]

Fixed · tight · fast
  • Size is known and unchanging (months, RGB channels, chessboard)
  • Hot paths where every byte and every cycle counts
  • Multi-dimensional grids and matrices
  • Interop with unmanaged APIs (P/Invoke, spans)
  • Read-only reference data

Pick List<T>

Dynamic · flexible · default
  • Size is unknown or changes at runtime
  • You need Add, Remove, Sort, Find
  • LINQ pipelines that materialise with .ToList()
  • The default 95% of the time
Best practice

Default to List<T>. Switch to an array only when you have a concrete reason — fixed size, measurable hot-path pressure, or interop requirements. Premature “arrays are faster” optimisation costs flexibility without measurable gain.

08Modern C# 14

The shape of these APIs hasn't changed in years, but the language around them has. Collection expressions, params collections, and Span<T> have quietly rewritten what idiomatic code looks like.

C# 12+ · unified literal syntax 
// Works for arrays, List, Span, ImmutableArray, any opted-in type
int[]          primes  = [2, 3, 5, 7, 11];
List<string>   colors  = ["red", "green", "blue"];
Span<byte>     header  = [0xDE, 0xAD, 0xBE, 0xEF];

// Spread operator — flatten existing sequences
int[] first  = [1, 2, 3];
int[] second = [4, 5, 6];
int[] all    = [..first, ..second, 7, 8];   // [1,2,3,4,5,6,7,8]
C# 13 · zero-allocation params 
// params is no longer array-only; ReadOnlySpan avoids the heap
static int Sum(params ReadOnlySpan<int> values)
{
    int total = 0;
    foreach (var v in values) total += v;
    return total;
}

int result = Sum(1, 2, 3, 4, 5);   // no heap allocation
Span<T> · stack-allocated view 
// Span is a safe view — no copy, no allocation, zero-copy slicing
int[] numbers = [10, 20, 30, 40, 50];

Span<int> window = numbers.AsSpan(start: 1, length: 3);
// window → [20, 30, 40], shares memory with the underlying array

window[0] = 99;
// numbers is now [10, 99, 30, 40, 50]
CollectionsMarshal.AsSpan · hot-path access 
using System.Runtime.InteropServices;

var list = new List<int> { 1, 2, 3, 4, 5 };

// Get a Span directly over the List's backing array — no bounds-check per access
Span<int> span = CollectionsMarshal.AsSpan(list);

for (int i = 0; i < span.Length; i++)
    span[i] *= 2;
// list is now [2, 4, 6, 8, 10]
Unsafe zone

The span returned from CollectionsMarshal.AsSpan becomes invalid the moment the list is resized. Do not Add or Remove while holding the span — use it purely for in-place read or mutate loops.

09Pitfalls & tips

Pitfall 01 · Index out of range

arr[arr.Length] throws IndexOutOfRangeException. Valid indices are 0 through Length - 1. Use the index-from-end operator arr[^1] to reach the last element safely.

Pitfall 02 · Mutating during iteration

foreach (var x in list) list.Remove(x) throws InvalidOperationException. Use list.RemoveAll(predicate) instead — it was built for exactly this case.

Pitfall 03 · Capacity never shrinks

Adding 1,000 items then removing 999 leaves the backing array at capacity 1,024. Call list.TrimExcess() if memory pressure matters, especially before long-lived storage.

Pitfall 04 · Array covariance

C# allows assigning string[] to object[], but writes are checked at runtime and throw ArrayTypeMismatchException. This is a legacy footgun — prefer List<T> or IReadOnlyList<T> to sidestep it entirely.

Best practice · Pre-sizing

When you know the final size of a list, pass it to the constructor: new List<Item>(capacity: expectedCount). No resize copies, no wasted allocations. Works for arrays too via new Item[expectedCount].

Best practice · Reach for the right tool

If you search by key constantly, a Dictionary<TKey, TValue> is roughly 10,000× faster than list.Find on 10k items. If you need constant-time insert in the middle, jump to LinkedList<T>.
