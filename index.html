§ 01 / Overview

A chain of nodes, each pointing to the next and back to the previous.

LinkedList<T> lives in
System.Collections.Generic
since .NET 2.0 (generic)

Where an array lays its elements down in a single contiguous block of memory, a linked list scatters them across the heap and stitches them together with pointers. Each element — a node — knows only about its immediate neighbours, and the list itself holds references to just the first and last nodes.

.NET's LinkedList<T> is doubly linked: every node carries a reference to both its predecessor and its successor. This gives you O(1) insertion and removal at either end, or at any position where you already hold a reference to the relevant node. The price you pay is per-node memory overhead and worse cache locality than a flat array.

A linked list is not a faster list. It is a different shape — chosen for the operations it makes constant-time.

Use it for queues that grow and shrink at both ends, for LRU caches paired with a dictionary, for editor undo stacks, and for any scenario where you insert or remove in the middle and already hold the node. For almost everything else, reach for List<T>.

§ 02 / Anatomy

Each node, a small three-field record.

LinkedListNode<T> is sealed; you cannot subclass it. Properties are read-only from the outside.

A LinkedListNode<T> exposes four properties to your code: Value, Next, Previous, and List. The list itself owns First, Last, and Count. There is no indexer — list[i] does not compile.

Program.cs
using System.Collections.Generic;

var chain = new LinkedList<int>([42, 17, 93]);     // collection expression (C# 12+)

LinkedListNode<int> head = chain.First!;      // Value = 42
LinkedListNode<int> tail = chain.Last!;       // Value = 93

Console.WriteLine(head.Value);               // 42
Console.WriteLine(head.Next!.Value);          // 17
Console.WriteLine(tail.Previous!.Value);      // 17
Console.WriteLine(head.Previous is null);     // True — head has no predecessor

§ 04 / Operations

Nine methods cover almost everything you need.

Each tab pairs the method with its complexity. The constant-time operations are what justify using this structure at all.

Every method on LinkedList<T> can be categorised by whether it targets an end (First/Last), a specific node reference, or a value to be searched. Select a tab below to see the idiomatic usage.

Prepends a value (or an existing detached node) before the current First. The new node becomes the head.

AddFirst / prepend
var queue = new LinkedList<string>();
queue.AddFirst("breaking");
queue.AddFirst("urgent");   // urgent → breaking

// Returns the new node; use it if you need to reference it later
LinkedListNode<string> node = queue.AddFirst("hot");
Console.WriteLine(node.Next!.Value);   // "urgent"

Appends to the tail. Paired with AddFirst, this lets you use a linked list as a double-ended queue (deque).

AddLast / append
var log = new LinkedList<string>();
log.AddLast("started");
log.AddLast("loaded config");
log.AddLast("ready");

Console.WriteLine(log.Last!.Value);   // "ready"
Console.WriteLine(log.Count);          // 3

Inserts immediately after a node you already hold. This is the operation where linked lists shine: no shifting, no reallocation — just two pointer assignments.

AddAfter / AddBefore
var lineup = new LinkedList<string>(["Alice", "Carol"]);

LinkedListNode<string> alice = lineup.First!;
lineup.AddAfter(alice, "Bob");     // Alice → Bob → Carol

LinkedListNode<string> carol = lineup.Last!;
lineup.AddBefore(carol, "Beth");   // Alice → Bob → Beth → Carol

Three overloads: remove by node reference (O(1)), remove by value (O(n), finds first match), or RemoveFirst / RemoveLast (O(1)).

Remove variants
var tasks = new LinkedList<string>(["lint", "build", "test", "deploy"]);

// O(1) — we already hold the node
LinkedListNode<string> lint = tasks.First!;
tasks.Remove(lint);

tasks.RemoveLast();                    // O(1) — drops "deploy"
bool removed = tasks.Remove("test");   // O(n) — scans for match

Find returns the first node whose Value equals the argument, or null. FindLast searches from the tail. Both are O(n).

Find / FindLast
var names = new LinkedList<string>(["Ada", "Grace", "Ada", "Linus"]);

LinkedListNode<string>? first = names.Find("Ada");       // index 0
LinkedListNode<string>? last  = names.FindLast("Ada");   // index 2

if (first is not null)
    names.AddAfter(first, "Lovelace");     // now O(1) — we hold the node

No indexer is provided. Walk with foreach (which yields values) or by following Next pointers manually (which yields nodes).

Traversal patterns
var chain = new LinkedList<int>([1, 2, 3, 4, 5]);

// Values only — simplest
foreach (var v in chain) Console.Write(v);

// Walk by nodes — lets you inspect Previous / Next
for (var n = chain.First; n is not null; n = n.Next)
    Console.WriteLine($"{n.Value} (prev: {n.Previous?.Value ?? -1})");

// Reverse traversal from tail
for (var n = chain.Last; n is not null; n = n.Previous)
    Console.Write(n.Value);   // 54321

Cache note
Even when Big-O says LinkedList wins, real hardware often says otherwise. Modern CPUs prefetch contiguous memory aggressively, so a List<T>'s O(n) shift over 1 000 integers can still beat a LinkedList's O(1) insertion because of cache locality. Measure before optimising.
§ 06 / Choosing

When to pick one over the other.

If you cannot answer "why not List?", the answer is List.

Pick

List<T>

  • You need index access (list[i])
  • Most work happens at the tail
  • You iterate far more than you mutate
  • Memory or cache behaviour matters
  • You use LINQ, sorting, binary search
  • The default choice, 95% of the time

Pick

LinkedList<T>

  • LRU caches (paired with a Dictionary)
  • Undo/redo stacks with arbitrary insertion
  • Playlist / queue with mid-sequence edits
  • You already hold node references
  • You need O(1) at both head and tail
  • Iterators must not be invalidated by inserts

A canonical win for LinkedList<T> is the LRU (least-recently-used) cache. A dictionary maps keys to node references in O(1), and the linked list moves recently-touched nodes to the front in O(1). No other built-in collection gives you both.

Sketch · LRU cache in ~20 lines
public class LruCache<K, V> where K : notnull
{
    private readonly int _capacity;
    private readonly LinkedList<(K key, V val)> _order = new();
    private readonly Dictionary<K, LinkedListNode<(K, V)>> _index = new();

    public LruCache(int capacity) => _capacity = capacity;

    public V? Get(K key)
    {
        if (!_index.TryGetValue(key, out var node)) return default;
        _order.Remove(node);                 // O(1)
        _order.AddFirst(node);               // O(1) — touch
        return node.Value.val;
    }

    public void Set(K key, V val)
    {
        if (_index.TryGetValue(key, out var existing)) _order.Remove(existing);
        else if (_order.Count == _capacity)
        {
            _index.Remove(_order.Last!.Value.key);
            _order.RemoveLast();             // O(1) — evict
        }
        _index[key] = _order.AddFirst((key, val));
    }
}
§ 07 / Modern idioms

What C# 14 & .NET 10 bring to the table.

Collection expressions and pattern matching make modern LinkedList code read almost like prose.

The LinkedList API itself is stable — .NET 10 has not changed its shape — but the surrounding language has. Collection expressions, is not null patterns, and extended property patterns all make calling code noticeably cleaner than the C# 5 era.

Modern idioms · C# 14
// ① Collection expressions — construct from literal
LinkedList<int> list = new([1, 2, 3, 4, 5]);

// ② Pattern matching on nullable node
if (list.Find(3) is { Value: var v, Next: { } next })
    Console.WriteLine($"Found {v}, next is {next.Value}");

// ③ Extension: materialise as array via LINQ
int[] snapshot = [.. list];           // spread into an array

// ④ Local functions over iterator state
IEnumerable<LinkedListNode<int>> Nodes(LinkedList<int> l)
{
    for (var n = l.First; n is not null; n = n.Next)
        yield return n;
}

foreach (var node in Nodes(list).Where(n => n.Value % 2 == 0))
    Console.WriteLine(node.Value);         // 2, 4

// ⑤ Primary constructor on a wrapper (C# 12+)
public class History<T>(int max)
{
    private readonly LinkedList<T> _items = new();
    public void Push(T item)
    {
        _items.AddFirst(item);
        if (_items.Count > max) _items.RemoveLast();
    }
}
§ 08 / Pitfalls

The rough edges that cut newcomers.

Almost all of these disappear once you think of LinkedList as "a sequence of node references", not "an array with slower indexing".
Pitfall 01 — no indexer
list[i] does not compile on LinkedList<T>. To get the i-th element you must traverse. If your code needs [i], you almost certainly want List<T> instead.
Pitfall 02 — a node belongs to one list
A LinkedListNode<T> can belong to exactly one LinkedList<T> at a time. Trying to AddFirst a node that is still attached to another list throws InvalidOperationException. Remove it first, or use AddFirst(node.Value) to copy the value.
Pitfall 03 — mutation during iteration
foreach over a LinkedList throws if you modify the list during the loop — the same rule as List<T>. If you need to delete during traversal, walk manually with Next and capture the successor before removing.
Safe deletion during traversal
var n = list.First;
while (n is not null)
{
    var next = n.Next;                  // capture FIRST
    if (n.Value % 2 == 0) list.Remove(n);
    n = next;
}
Pitfall 04 — null after the ends
First.Previous and Last.Next are both null. Dereferencing them is an NRE waiting to happen. Use nullable-aware patterns (is not null, ?.) systematically.
Note — not thread-safe
Like every collection in System.Collections.Generic, LinkedList<T> is not thread-safe for writes. For concurrent scenarios reach for ConcurrentQueue<T>, ConcurrentBag<T>, or explicit locking.
