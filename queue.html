Queue<T>

First-in, first-out. Items enter at the back, leave from the front — the discipline of fair ordering. Backing nearly every task scheduler, message buffer, and breadth-first search ever written, Queue<T> is the quiet workhorse of systems that have to wait their turn.

01Overview

A queue enforces the fairest possible rule: whoever arrived first leaves first. Items enter at the back via Enqueue and leave from the front via Dequeue. No queue-jumping, no shortcuts — hence FIFO, first-in, first-out.

If Stack<T> is a pile of plates, a queue is the line outside a post office: everyone patient, everyone in order. When you need arrival order preserved — print jobs, tasks dispatched to worker threads, messages between services, levels of a tree explored one layer at a time — a queue is almost always the right shape.

Namespace

Queue<T> lives in System.Collections.Generic. Internally it's backed by a circular buffer — a fixed-capacity array with head and tail indices that wrap around. This is the secret sauce that keeps both Enqueue and Dequeue at O(1) without any shifting. For thread-safe use, reach for ConcurrentQueue<T>.

Picture a conveyor belt moving left. New items enter on the right (Enqueue) and drop off on the left (Dequeue). The item at the front is the oldest; the item at the back is the newest.

Program.cs · a print job queue 
using System.Collections.Generic;

var printJobs = new Queue<string>();
printJobs.Enqueue("invoice.pdf");        // arrives first
printJobs.Enqueue("report.docx");
printJobs.Enqueue("photo.jpg");          // arrives last

Console.WriteLine(printJobs.Count);        // 3
Console.WriteLine(printJobs.Peek());       // "invoice.pdf"  — still in queue
Console.WriteLine(printJobs.Dequeue());    // "invoice.pdf"  — served first
Console.WriteLine(printJobs.Dequeue());    // "report.docx"
Console.WriteLine(printJobs.Count);        // 1

Watch for this

Enqueue slides in from the right (the “back”) with a small settle — that's queue.Enqueue(x) in O(1). Dequeue ejects the front item to the left — also O(1), thanks to the internal circular buffer. No shifting, no copying. Peek flashes the front amber without changing anything.

04Core operations

Six methods carry almost every use of a queue. As with Stack<T>, the Try* variants are the modern, exception-free way to access the front.

Adds an item to the back. The circular buffer grows (doubles) only when capacity runs out — otherwise the tail index just advances.

Enqueue / arrive at back
var tasks = new Queue<string>();
tasks.Enqueue("fetch user");
tasks.Enqueue("validate input");
tasks.Enqueue("write to db");

// Front → "fetch user" | Back → "write to db"
Console.WriteLine(tasks.Count);        // 3

// Pre-size if you know the throughput ceiling
var hot = new Queue<int>(capacity: 1024);

Removes and returns the front item. Throws InvalidOperationException on an empty queue — always prefer TryDequeue unless you've already checked Count.

Dequeue / leave from front
var q = new Queue<int>([10, 20, 30]);
// Collection expression preserves insertion order — 10 is at the front

int first = q.Dequeue();      // 10
int second = q.Dequeue();     // 20
Console.WriteLine(q.Count);       // 1

// Empty queue throws — dangerous overload
var empty = new Queue<int>();
// empty.Dequeue();   // InvalidOperationException!

Returns the front without removing it. Useful when the decision to actually dequeue depends on inspecting the value first.

Peek / inspect front
var events = new Queue<Event>();
events.Enqueue(new Event("click", priority: 3));
events.Enqueue(new Event("scroll", priority: 1));

// Only handle if it's urgent enough
if (events.Peek().Priority >= 2)
    Handle(events.Dequeue());

The modern, exception-free variants. Idiomatic for any code that can't guarantee the queue is non-empty — which is most code.

TryDequeue / TryPeek
var mailbox = new Queue<Message>();

// Drain loop — clean and exception-free
while (mailbox.TryDequeue(out var msg))
    Process(msg);

// Peek without risking an exception
if (mailbox.TryPeek(out var next))
    Console.WriteLine($"next: {next}");
else
    Console.WriteLine("nothing pending");

Linear scan from front to back. If your code relies on Contains, consider pairing the queue with a HashSet<T> for O(1) membership checks.

Contains · linear search
var pending = new Queue<int>();
var pendingSet = new HashSet<int>();   // mirror for fast lookup

void Add(int id)
{
    if (pendingSet.Add(id))                // O(1) — deduped
        pending.Enqueue(id);                  // O(1)
}

// Avoid scanning the whole queue every time
bool isPending = pendingSet.Contains(42);   // O(1)

Iteration walks from front to back — the natural, insertion-preserving order. Unlike Stack<T> this lines up with intuition.

foreach / ToArray
var q = new Queue<int>();
q.Enqueue(1);
q.Enqueue(2);
q.Enqueue(3);

foreach (var n in q)
    Console.Write(n);          // 123 — front to back, as inserted

int[] snapshot = q.ToArray();
// snapshot: [1, 2, 3]

// Iteration does NOT dequeue — the queue is unchanged
Console.WriteLine(q.Count);       // 3

The circular buffer trick

Queue<T> is backed by a plain array, but with two integer indices — _head (front) and _tail (back). Dequeue increments _head; Enqueue increments _tail. Both wrap around to zero at the end. Nothing ever shifts. When _tail catches up to _head, the array doubles — the same capacity-growth policy as List<T> and Stack<T>.

06When to choose which

Queue<T> and Stack<T> are the same collection in two mirror-image disciplines. The question is simply: which end do you want to pull from?

Pick Queue<T>

FIFO · fair ordering
  • Task / job schedulers (oldest task first)
  • Breadth-first search of graphs and trees
  • Producer ↔ consumer message buffers
  • Print queues, event pipelines, log shipping
  • Web server request dispatch
  • Simulation of real-world waiting lines

Pick Stack<T> instead

LIFO · the opposite discipline
  • Undo & redo history
  • Depth-first search of graphs and trees
  • Expression parsing, balanced brackets
  • Backtracking algorithms (mazes, N-queens)
  • Call-stack simulation or trampolining
  • See — Module 03
Decision rule

If order of arrival matters and you want the oldest served first, use a queue. If you want the newest first, use a stack. If you need priorities (most important first), reach for PriorityQueue<TElement, TPriority> — a heap-backed specialisation added in .NET 6.

07BFS graph traversal

The canonical queue problem. Breadth-first search explores a graph level by level — visiting every neighbour of the start node before any of their neighbours. The queue is what makes it level-order: as you discover new nodes you enqueue them at the back, and you always dequeue the oldest from the front. The result is a wave expanding outward from the source.

The algorithm, 15 lines 
static List<string> Bfs(
    string start,
    Dictionary<string, List<string>> graph)
{
    var visited = new HashSet<string> { start };
    var queue   = new Queue<string>();
    var order   = new List<string>();

    queue.Enqueue(start);

    while (queue.TryDequeue(out var node))
    {
        order.Add(node);
        foreach (var next in graph[node])
        {
            if (visited.Add(next))           // true if NEW
                queue.Enqueue(next);
        }
    }
    return order;
}
Why this pattern is everywhere

Replace “graph” with any level-ordered exploration and the same skeleton works: directory tree traversal, web crawling, spreading simulations, shortest-path-in-unweighted-graphs, multi-source flood fill, even CSS selector matching on a DOM. A Queue<T> plus a HashSet<T> for dedup is one of the most reused pairings in all of computing.

08Modern C# 14 idioms

The Queue<T> API is stable, but the surrounding language keeps tightening what queue-using code looks like.

Modern idioms · C# 14 on .NET 10 
// ① Collection expressions — insertion order preserved
Queue<int> q = new([10, 20, 30]);
//     10 is at the front, 30 at the back

// ② TryDequeue drain loop — no exceptions, no Count checks
while (q.TryDequeue(out var item))
    Console.WriteLine(item);       // 10, 20, 30

// ③ Spread into an array — front-to-back order
var log = new Queue<string>();
log.Enqueue("a"); log.Enqueue("b"); log.Enqueue("c");
string[] snap = [.. log];                // ["a", "b", "c"]

// ④ Bounded fixed-size ring buffer — 10 lines
public class RingBuffer<T>(int capacity)
{
    private readonly Queue<T> _items = new(capacity);

    public void Add(T item)
    {
        if (_items.Count == capacity) _items.Dequeue();
        _items.Enqueue(item);
    }

    public T[] Snapshot() => [.. _items];
}

// ⑤ PriorityQueue — when "fairness" should mean "most important first"
var pq = new PriorityQueue<string, int>();
pq.Enqueue("email",   5);
pq.Enqueue("alert",   1);   // lower = higher priority
pq.Enqueue("cleanup", 9);
Console.WriteLine(pq.Dequeue());    // "alert"
PriorityQueue<TElement, TPriority>

If you need “most-important-first” rather than strict FIFO, reach for PriorityQueue<TElement, TPriority>, added in .NET 6 and unchanged since. It's a binary-heap implementation with O(log n) enqueue and dequeue — perfect for scheduled jobs, A* search, and Dijkstra's algorithm.

09Pitfalls

Pitfall 01 · Dequeue on empty throws

Dequeue() and Peek() both throw InvalidOperationException when the queue is empty. Always prefer TryDequeue / TryPeek unless you have an iron-clad invariant that guarantees non-empty.

Pitfall 02 · Don't use List as a queue

list.RemoveAt(0) is O(n) — it shifts every remaining element left one position. On a list of 10,000 items this is devastating in a tight loop. Queue<T> with its circular buffer is O(1) for the same operation. If you find yourself calling RemoveAt(0), switch to a queue.

Pitfall 03 · Capacity never shrinks on Dequeue

Just like List<T> and Stack<T>, the internal array keeps its high-water-mark capacity even after everything is dequeued. Call TrimExcess() on long-lived queues that have briefly grown large.

Pitfall 04 · Contains is O(n)

If your algorithm has to ask “is X already in the queue?” repeatedly, maintain a parallel HashSet<T> for O(1) membership. This is the textbook BFS pattern — the visited set is never the queue itself.

Not thread-safe

Queue<T> is not safe for concurrent access. For producer – consumer pipelines reach for ConcurrentQueue<T> from System.Collections.Concurrent — lock-free Enqueue, TryDequeue, TryPeek. Or for blocking semantics (consumers wait for producers), System.Threading.Channels.Channel<T>.
